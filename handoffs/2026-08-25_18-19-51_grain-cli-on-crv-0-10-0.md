# Handoff: grain watch runs on crv 0.10.0 — one workaround deleted, one replaced

> Predecessors: `handoffs/2026-08-21_14-55-03_grain-cli-shipped.md` (what shipped) and
> `handoffs/2026-08-21_13-57-22_grain-cli-crv-vs-video-vision.md` (why crv). See CLAUDE.md for
> dev guidance.

## What Happened

The three upstream issues filed on 2026-08-22 were answered the same day. Two shipped in crv
**0.10.0**, and this session moved the CLI onto them.

- **#16 `--from`/`--to`** — shipped. The maintainer took the timestamp trap reported from
  experience (a report citing 00:38:08 for a frame at 30:32): an input-side `-ss` restarts
  output PTS at zero, so window-relative timestamps go quietly wrong. The framing *"a window
  should shift the analysis, not the clock"* is now the comment above `_shift_times()` and the
  name of the regression test.
- **#17 `--frame-width`** — shipped. Default 640, aspect kept, both extraction paths.
  Explicitly: *"Your second ffmpeg pass should be retirable now."* He declined
  `--frame-scale source` (one flag beats two).
- **#18 Grain as a native crv source** — closed `not_planned`, on good reasoning: a second auth
  story and a second vendor API carried by every crv user, and the `406`-on-formatted-transcript
  edge we reported means a fallback would be needed on day one. He offered to link the Grain
  wrapper in the README as a community tool, and said sidecar-transcript friction from a
  wrapper (cue formats, `--text-anchors` alignment) *is* in scope if we hit any.

**The upgrade is not clean, and the reason is the headline of this handoff.** crv 0.10.0's
`--to` silently discards every frame timestamp. `_window_args()` puts `-t` on the output side,
so ffmpeg's `showinfo` logs the whole pass while only the windowed frames get written;
`extract_frames()` ends with `return count, (times if len(times) == count else [])`, the counts
disagree, every time is thrown away, every record gets `t=None`, `write_frames_json()` bails on
`if not kept`, and `MANIFEST.txt` simply omits its `frame timestamps:` line. Nothing errors.

Isolated on a 20-second clip:

| flags | `frames.json` |
|---|---|
| none | yes |
| `--frame-width 1280` | yes |
| `--from 5` | yes |
| `--to 15` | **no** |
| `--from 5 --to 15` | **no** |

Raw ffmpeg reproduction: `-ss 5 -i clip.mp4 -vf "select=…,showinfo,scale=640:-1" -t 10` logs 12
showinfo lines and writes 4 jpgs.

So the CLI passes crv `--from` only. An upper bound is imposed with a **head clip** — `0 → to`,
origin unmoved, so the clip's clock *is* the source clock — which is what keeps the offset
arithmetic deleted rather than merely relocated. The exported subtitle is hardlinked to the
clip's stem unmodified (same clock, nothing to trim), so Whisper still never runs.

Everything else got simpler. `clipMedia()`, `trimSubtitle()` and `--precise` are gone.
`--full-res` now probes the source width with `ffprobe` and hands it to crv as `--frame-width`;
`--frame-width <px>` sets it explicitly and wins. `frames-hires/` became `frames-by-time/`: the
same frames **hardlinked** under absolute source timecodes instead of re-encoded copies, so it
costs no disk. `frame-map.tsv` and `grid-map.tsv` are written on every watch and live in the
analysis directory. `requireCrv()` rejects a pre-0.10.0 binary by looking for `--frame-width`
in its `--help`, instead of letting it die inside argparse complaining about our flags.

Docs updated to match: `SKILL.md`, `references/cli-reference.md`, `references/crv-output.md`,
and `agents/grain-recording-watcher.md` — the agent's "windowed timestamps are clip-relative,
add the offset" rule is now its inverse, with an explicit warning not to re-apply an offset.

## Key Decisions Made

- **Bound `--to` with a head clip rather than waiting upstream or accepting missing
  timestamps.** Silent loss of every frame timestamp is the exact failure class this CLI exists
  to prevent. Clipping from zero (rather than from `--from`, as the old code did) is what makes
  the fix free of offset math: the clip and the source share a clock.
- **`frames-by-time/` hardlinks rather than copies.** crv already extracts at the requested
  width, so a second copy of a 3840px frame set would be pure waste. Verified: same inode.
- **Millisecond disambiguation on colliding seconds.** A one-minute window kept 58 frames that
  collapsed onto 54 second-resolution names; the old code counted the 4 collisions as "already
  present" and dropped them silently. Now every member of a collision carries milliseconds, so
  a bare `tHH-MM-SS` name always means exactly one frame.
- **Grid cells were checked, not assumed.** `make_grids()` hardcodes `cell_width=480`, so
  `--frame-width` does not inflate contact sheets and `--crop-in-grid` geometry is untouched.
- **Accept the un-windowed sidecar transcript.** `existing_subtitles()` takes no start/end, so
  `transcript.txt` covers the whole call even for a one-minute window. Documented and printed
  as a note rather than worked around; extra context is harmless.

## Known Issues

- **The crv `--to` bug is not reported upstream.** The reproduction above is ready to paste.
  Landing a fix deletes the head clip, its ffmpeg dependency, and the disk it costs.
- **A `--to` window writes a head clip beside the media** — 100MB for a 32-minute bound on the
  test recording. Reused across runs, never cleaned up automatically.
- **`~/Documents/Grain/2026-08-10_engineering-sync_eb542359/` holds 138MB of dead clips**
  (`_00-00-00_00-26-00.mp4`, `_00-26-00_00-47-19.mp4`) produced by the old clip path, plus the
  new 100MB head clip. Safe to delete the first two.
- **Analyses produced before 0.10.0 are still clip-relative.** Both cached `crv-out_*`
  directories predate the upgrade, so their `frames.json` numbers are window-relative and their
  `frames-hires/` names came from the old ffmpeg pass. Check a directory's age before trusting
  its numbers.
- **`--crop-in-grid` still has only ever run against one 1280x720 source** — unchanged by this
  work, and the factor should print `(1920÷480)` = 4.0 on any 1920-wide call.
- **Two paths remain unexecuted:** the `.grain-lock` refusal and the `crv-out…-2` side-step.
  Two concurrent watches on the cached recording would settle both cheaply.
- `pipx` cannot run inside this session's sandbox (`~/Library/Logs/pipx` is not writable), and
  neither `pip` nor Python can do TLS here (`OSStatus -26276`) though `curl` can. The upgrade
  was run by the user. Reading an installed package's source works fine via the pipx venv path.
